# Constant-time audit: current vendored k256, 2026-11-06

**Normalized-point equality's secret-dependent branch is fixed on all five
audited configurations.** The `ct-fix-normal-eq` change keeps both identity
predicates as Choices and evaluates them unconditionally. Static inspection and
emulated x86 taint confirm removal of the branch; they do not certify hardware
timing or the whole library. The Apple follow-up documents caller-managed
platform requirements and adds focused native normalization evidence below.
It installs no runtime timing mitigation or universal hardware guarantee.

**On the tested M5 Max/macOS host, normalization timing depends on the input's
coordinate representation in the default context.** The focused experiment
repeatedly flags both identity/projective inputs and two representations of the
same nonidentity point with DIT disabled. This matters for secret-derived
projective points, including ordinary nonidentity points. Those contrasts do not
flag in the API-enabled runs; enabling the mode is not a proof of safety, and
secp256kfun does not enable it for callers. The experiment changes several
coordinates and does not isolate z or identify a particular instruction or
hardware mechanism.

The strongest positive result is a completed binary relational check of seven
scalar roots, separately on two pinned RV32 builds, under the initialization and
observation model below. Other roots have manual inspection and/or sampled taint
evidence with explicit gaps. Review records are Codex's candidate classifications
for Clank peer review, not approval generated by a script.

## Contract and dispatch

The obligation is on **`impl TimeSensitive for ConstantTime`**, not the trait in
isolation: VariableTime also implements it. `contracts.json` maps all **26** trait
methods to **28** exported, non-inlined Secret API roots, or gives a reason for
three currently unused ConstantTime entry points. Coverage rejects method/root
additions or removals and missing taint harness cases. Trait extraction stops at
its matching brace. The unused-method guard scans all Rust source outside backend/
for qualified references, including aliases, `T::method`, and `<T as
TimeSensitive>::method`. This conservative text check is not Rust name resolution
and may require review of a harmless reference.

`op.rs` currently calls ConstantTime directly for the audited operations, even
where an operand is Public. Normal/non-normal point specialization is decided by
public type markers. The wrappers exercise normal and non-normal multiplication,
a secret point, mixed normality double multiplication, dot products, arithmetic,
normalization, predicates and both conditional-negation outcomes. Public iterator
implementations other than these slice/array instantiations are not covered.

Secret data are scalar values, point coordinates (including identity where Zero
permits it), and conditional-negation booleans. Pointers, lengths, layouts,
allocation outcomes and type markers are public. Values must satisfy their safe
API invariants, including NonZero inversion and normalized Normal points.
Returned values and predicates are outputs; the harness does not branch on them
inside the audited region. Serialization, parsing, random generation, hash-to-curve,
and whole signing protocols are outside this inventory.

## Static inspection and findings

The analyzer follows direct calls, tails and cross-function conditional transfers;
it handles merged root aliases, RISC-V AUIPC/JALR pairs and x86 GOT relocations.
Every reached instruction contributes to a fingerprint, rather than just a branch
count. It inventories loads **and stores**, multiplier/divider candidates, excluded
leaves and unresolved transfers. Unknown decoded instructions and name collisions
fail the run. Each conditional branch offset has a classification in `reviews/`.

| Configuration | Reached functions | Conditional branches | Memory accesses | Multiply candidates | Unresolved transfers |
|---|---:|---:|---:|---:|---:|
| darwin | 76 | 86 | 3586 | 281 | 0 |
| arm-linux | 77 | 86 | 3579 | 281 | 1 |
| x86 | 76 | 81 | 5427 | 160 | 5 |
| rv32 | 71 | 71 | 7950 | 788 | 0 |
| rv32-firmware | 61 | 143 | 4123 | 762 | 0 |

These are static inventories, not proof coverage counts. Register provenance in
`analysis.json.gz` is a nearest linear-definition aid: it is not SSA, alias
analysis, a control-flow fixpoint or a secret-taint checker. Manual address
inspection found fixed limb/stack offsets, public slice positions and full table
scans, but cannot establish universal address independence for all these functions.

The pre-fix normalized equality implementation contained
`Choice::from((lhs.is_zero() && rhs.is_zero()) as u8)`. The `&&` skips the right
identity test depending on the left point. It became `b.eq` on ARM, `je` on x86
and `beqz` on RV32, including the size/fat-LTO build: a real contract violation on
valid Zero points. **ct-fix-normal-eq** replaces it with
`lhs.is_identity() & rhs.is_identity()`, keeping both values as Choices without
the bool round trip. The existing coordinate comparison and returned bool remain.

Every equality root lost its single conditional branch. The complete reached
equality subgraphs now have zero conditional branches, zero unresolved transfers
and no excluded leaves. Manual inspection found only fixed point-field and stack
addresses, including the unchanged field-comparison and `subtle::black_box`
helpers. This is inspected machine-code evidence, not a universal formal proof
or an operand-latency claim:

| Configuration | Equality functions | Branches before → after | Memory accesses after | Multiply candidates after |
|---|---:|---:|---:|---:|
| darwin | 4 | 1 → 0 | 32 | 2 |
| arm-linux | 4 | 1 → 0 | 32 | 2 |
| x86 | 4 | 1 → 0 | 41 | 2 |
| rv32 | 4 | 1 → 0 | 66 | 2 |
| rv32-firmware | 6 | 1 → 0 | 96 | 1 |

Outside equality, changed code fingerprints come only from relocated constant,
GOT and arena addresses or disassembler annotations. Reached function sets,
call edges, exclusions, unresolved transfers, branch offsets and memory counts
are unchanged there. Respectively 19, 25, 18, 27 and 25 of the 28 complete root
fingerprints are unchanged. Exact deltas and hashes are in `equality-fix.json`.
Every root gets a fresh review note because source/harness configuration changed.
The functional regression covers both identities (including cancellation-produced
identity), either side identity, equal nonidentity points, and P versus -P.

The scalar inversion guard is different: `CtOption::unwrap()` tests
`!scalar.is_zero()`. It is secret-derived and Memcheck flags it, but the public
`Scalar<NonZero>` type precondition makes the branch invariant on valid inputs.
This is classified explicitly, with no declassification inside inversion and no
blanket Valgrind suppression.

Other reviewed branches depend on fixed exponentiation chains, fixed 32-window /
four-doubling loops, full eight-entry table scans, public slice lengths and bounds,
capacity/allocation results, or copy alignment/counts. `mul_shift_var` branches
and limb indices depend on its shift parameter: both reachable decomposition calls
pass literal **384**, not a secret shift. The ARM double-multiply `tbnz` tests the
public two-element iterator flag stored as 0 then 1, not a scalar bit.

The x86 analyzer leaves five register-indirect calls visible in dot/double
multiplication. Manual GOT inspection identifies memcpy, but no general indirect
call resolution or libc proof is claimed. ARM Linux has an unresolved
`memcpy@plt` transfer. Darwin's `_memcpy` stub and host allocators are explicit
excluded leaves; panic paths are excluded under the listed public-size/valid-input
assumptions. RV32 copy/set routines are included and their branches inspect public
pointers and counts. No `__multi3`, divide or remainder instructions/helpers were
found in the reached arithmetic. RV32 uses `mul`/`mulhu`; ARM uses `mul`, `umulh`,
`madd`; x86 uses `mulq`/`imulq`.

A separate functional issue surfaced: the allocating point dot product panics on
empty input at `vendor/k256/mul.rs`'s `tables1[0]`. Length is public, so this is not
a secret-timing leak. Dynamic point-dot cases use lengths one and two (including
unequal lengths); scalar dot also tests zero length. No claim is made that the
allocating empty point-dot behavior is correct.

## Relational binary evidence

BINSEC **0.11.3**, Z3 **5.3.3**, reran on the actual linked RV32 images after the
equality fix. Both profiles
completed all paths for scalar **add, subtract, multiply, negate, equality,
is-high, is-zero**. Initialization fixes public, aligned, disjoint argument/output
buffers, stack and return sentinel. Each input is a symbolic 256-bit canonical
scalar constrained below the group order; it uses the binary's little-endian
8x32 representation. The model observes control-flow and demand memory addresses,
not arithmetic operand latency, output equality, speculation or prefetch.

Each production case completed one path with zero pending/discontinued paths and
failed assertions; see the saved scripts and full logs in
`evidence/rv32{,-firmware}/relational/`. The one-million-instruction bound and
90-second limit were not reached. Both positive controls were reported insecure:
one branches on a secret byte, the other indexes a 256-byte table by it. The runner
rejects timeouts, unknowns, unsupported instructions, tool errors, zero completed
paths, nonzero pending/discontinued paths, and mismatched results. A `secure` word
in an incomplete log is not accepted.

This supports branch/address independence for those exact seven roots, valid
symbolic scalar inputs and fixed initialization, under BINSEC's ISA semantics.
It does not cover alternate public pointer layouts/aliasing, all point operations,
inversion, all iterators, hardware time, or functional arithmetic correctness.

During the original audit, an x86 scalar-is-zero attempt aborted in the Unisim
decoder with
`ProcessorBase::Undefined`. Its SSE2-containing body was not proven or disproven;
the logs are preserved in `evidence/x86/binsec-gap/`. The RV32 checker was used
because it completed, not because that tool failure could be counted as success.

## Emulated semantic taint evidence

Valgrind **3.22.0** ran in our own QEMU x86_64 Ubuntu 24.04 Lima VM `ct-x86`.
This is **emulated semantic instrumentation**, never native x86 timing evidence.
Memcheck client requests mark scalar limbs, entire secret point values and
conditional predicates undefined, preserving public pointer/length metadata.
The marker refuses to run silently without Valgrind.

Twelve deterministic valid-input fixtures exercise all 28 roots (**336 calls**):
zero where allowed, one, minus one, identity, equal and opposite points, both
predicate outcomes and seeded random cases. Defined-input control: zero findings.
Case 6 now supplies **both normalized operands Zero**, alongside cases 2 and 5
with just one Zero operand. The same 12-case/336-call inventory is retained.
Injected branch/address controls: exactly one `UninitCondition` / `UninitValue`,
respectively, and exit 99. Two complete tainted runs after the fix report only
the NonZero inversion invariant: `UninitCondition` at `0x1025B9D`.
The equality finding is gone; no secret-dependent address finding was observed
in these executions. This is sampled path coverage, not a proof.

`taint-findings.json` matches the exact error kinds and first-stack frames/IPs;
it requires an explicit classification for every finding. The equality entry was
removed only after the fixed image passed; the NonZero invariant remains.
It does not install suppressions,
and any new, missing or changed finding fails for review. Green here means
“no additional findings, controls working,” **not “CT compliant.”** Full XML,
stdout and binary hash are retained. With linker debug metadata stripped, stacks
retain symbol names and exact instruction addresses but no inlined DWARF frames.

## Native Mac timing and calibration before the equality fix

Host: **Apple M5 Max, macOS 27.0.1 (26A434)**. The separate `ct_timing` executable
uses the same wrappers and locked dependencies, release opt=3/one codegen unit/no
LTO, with rustc's default host CPU. It is separately hashed; it is not the static
`ct_audit` image. Three seeds run 100,000 samples per row, with randomized class
order and fixture generation outside timing. The Welch estimator and pooled
90/75/50-percent crops carry forward the earlier arith-backend harness.

The original audit's final experiment used the **same executable** for default
mode and Apple's
`timingsafe_enable_if_supported()` mode, alternating modes for each seed. DIT was
read as 0 before every run, stayed 0 in default mode, and read `0x1000000` during
timing-safe mode; the previous state is restored on exit. The ordinary library
does not enable this mode as part of this change.

Below is the maximum absolute t statistic across the raw and three pooled crops;
4.5 is an investigation threshold, not a corrected multi-test p-value.

| Comparison | Default seeds 1 / 2 / 3 | Timing-safe seeds 1 / 2 / 3 |
|---|---|---|
| kG one/random | 3.40 / 17.67 / 21.89 | 1.74 / 1.74 / 1.02 |
| kG then normalize one/random | 10.39 / 20.17 / 10.28 | 1.65 / 1.21 / 1.40 |
| normalize identity/nonidentity | 43.19 / 53.95 / 48.54 | 1.68 / 1.83 / 1.51 |
| normalized equality identity/nonidentity | 7.60 / 23.13 / 8.98 | 1.64 / 5.73 / 1.30 |

All identical-input controls stayed below 2.97. kP fixed/random and scalar
inversion one/random stayed below 2.80. A known real branch was not consistently
detected with DIT enabled, illustrating why a statistical pass is insufficient.
The equality test also changes its returned boolean; the harness black-boxes the
result without conditional processing. Static and taint evidence establish the
internal branch independently of this timing comparison.

Positive calibration injects dependent integer-add sequences after fixed-input
kG. Each delay is measured separately against the zero-add call in 101 randomized
pairs of 1,024-call batches, reporting median/p10/p90 nanoseconds. These are
measured incremental costs, not assumed cycles per instruction. Four adds
measured indistinguishably from zero. Across the six final runs:

| Adds / measured incremental cost | Any class-difference flag | Expected direction | Opposite direction |
|---|---:|---:|---:|
| 16 / 0.6–0.8 ns | 0/6 | 0/6 | 0/6 |
| 64 / 7–9 ns | 0/6 | 0/6 | 0/6 |
| 256 / 50–64 ns | 5/6 | 4/6 | 4/6 |
| 1024 / 239–324 ns | 6/6 | 6/6 | 4/6 |

A run flags when any raw or cropped statistic has `abs(t) > 4.5`. Class 1
receives the delay, so the expected direction is `t < -4.5`; opposite-direction
flags have `t > 4.5`. The direction columns overlap when crops disagree. For
example, default seed 2 with 1024 adds has a 375-ns slower class-1 median, but
`t90 = +13.62`, `t75 = -6.46`, `t50 = -8.38` and `t-all = -0.20`.
Pooled cropping of these multimodal, timer-quantized distributions can reverse
the direction. Operation flags can also be confined to particular crops.

This setup repeatedly detected a class difference in the roughly 0.3-microsecond
injection experiment at this workload/sample count, including an expected-direction
flag in all six runs. The conflicting cropped signs prevent treating the absolute
flag counts as a calibrated delay-detection threshold. They do **not** bound all
undetected leakage below that number or guarantee 50-ns detection.
Delay calibration occurs outside the measured cryptographic
operation; instruction overlap, timer granularity and scheduling affect it.
The machine was not isolated or core-pinned; other work/VMs and frequency changes
are possible confounders. TSV summaries and exact pins are retained; individual
sample streams were not saved. Timing is audit evidence, not a flaky PR gate.

The disappearance of repeated kG/normalization flags when enabling timing-safe
mode is evidence of a platform-context dependency, not identification of one
specific leaking instruction or a complete mitigation proof. The focused Apple
follow-up and public platform contract are described below.
No blanket guarantee is available for the default Mac execution context.

## Apple platform contract and focused normalization experiment

The public [timing/platform requirements](../README.md#timing-and-platform-requirements)
are linked from Secret, Secrecy, Point and Scalar rustdoc. Secret expresses an
implementation obligation; it does not configure the CPU or certify compiled
code and whole protocols. Apple callers must establish a supported synchronous
context before handling sensitive data, handle OS availability separately from
hardware support, and restore the prior state with the opaque token on the same
thread, including early exits. Such a scope must not span await/thread migration.
The library provides neither automatic enablement nor an older-OS fallback.

[Apple's maintained ARM64 guidance](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)
and the local SDK `timingsafe.h` were checked on 2026-11-06. API availability begins
at macOS 15.2, iOS/iPadOS/tvOS 18.2, watchOS 11.2 and visionOS 2.2. An available API
can have no effect on unsupported hardware. Apple's mode uses device-appropriate
safeguards, including speculation barriers, in addition to DIT. Therefore the
API-mode contrast cannot be attributed to the DIT bit alone. Our host reports
`hw.optional.arm.FEAT_DIT=1`; this is CPU support, not a guarantee for every
instruction. We have not established full instruction-latency, speculative or
prefetch safety, even with the mode enabled.

### Actual timing executable comparison

The **separately linked timing executables**, before and after the equality fix,
were disassembled with the pinned LLVM tools. Each normalization subgraph reaches
six functions, with three conditional branches, 443 memory-access instructions,
109 multiply candidates and no unresolved transfers. All six normalized instruction
fingerprints match. Five function locations, including the root, match; only
`subtle_ng::black_box` moves from `0x10003de0c` to `0x10003de00` (12 bytes).
The six raw instruction-operand differences are calls to that helper: two in
field inversion and four in point normalization. Their opcodes are unchanged.

The three branches are fixed exponentiation loops in field inversion, with
counters initialized to 44, 88 and 44. This
comparison does not establish that the helper's alignment caused the changed
statistics, and it does not measure a change in leakage magnitude. Scheduling,
frequency, code/data layout and other process context remain possible confounders.
The original timing sources, hashes and results are preserved, rather than being
relabeled as measurements of the current input tree. Disassembly, symbol layouts,
normalization analyses and exact operand deltas are in
`evidence/darwin/apple-normalization/`.

### Focused experiment

The audit-only `normalize` option uses 16 black-boxed calls to `audit_normalize`
per sample, with 100,000 randomly ordered samples per row and seeds 1, 2 and 3.
The reported medians are **nanoseconds per entire batch**, not per operation.
Fixtures are made outside the timer: identity, a nonidentity point obtained by
adding two normalized points, and that same point normalized then converted back
to the non-normal type (z=1). Equality of the two nonidentity points is asserted.
This holds their affine value constant but changes their coordinate representation;
it does not isolate z, inversion, an individual instruction or a prefetch mechanism.
Both nonidentity representations also have identical-input controls. The positive
control adds 4,096 dependent integer adds after a fixed-input batch in class 1.

One separately pinned native executable is used in both modes, default then
API-enabled for each seed, on the same M5 Max/macOS host and release profile as
before. Our VM is stopped and audit builds are finished before timing. The machine
is still unisolated and not core-pinned. The harness records DIT before, during
and after restoration; nested scopes and unwind restoration are separately tested.
All TSV summaries, seed fixtures, commands, source/harness/compiler/profile pins
and a parsed summary are retained in `evidence/darwin/apple-normalization/`.
The underlying sample streams are not retained; this remains an investigation,
not a CI timing threshold or a hardware proof. This optional experiment binary
and its restoration test require a DIT-supported ARM Mac and macOS 15.2 or later:
they directly link the API and read DIT. Applications need their own availability
and support handling as described in the public contract.

The focused executable's normalization subgraph has the same six function
fingerprints and control/address structure as the post-equality timing executable.
All six function locations change. Its 110 raw operand deltas are 107 calls to
the same named functions and three fixed-loop branches to the same relative
offsets; only absolute addresses change. The batch body contains 16 unrolled
direct calls to the wrapper, so the repeated workload was not optimized away.
These comparisons concern the actual timing images, independently of the static
five-target images. See `focused-differences.json` and `batch-disassembly.json`.

DIT reads 0 before all six runs, remains 0 in default mode, reads `0x1000000`

contrast reproduces in all default-mode seeds; so does the comparison between
two representations of the **same nonidentity point**. Neither flags in the

the mechanism. Identity/z=1 has one isolated default-mode flag (seed 2's 50-percent
crop); that comparison is not consistently null. The identical controls all stay
below 2.74.

The positive control has an expected-direction flag in every run. Its class-1
median is 918–1,083 ns slower per batch; default seed 1 also has an opposite-sign
50-percent crop (`t50=+11.20`, while `t90=-23.72`). These are noisy, cropped,

in t across seeds does not establish a corresponding change in leak size.
The strongest supported conclusion is repeated input-class timing dependence
in the tested default execution context, with no detection for those contrasts
in these API-enabled runs. This supports a documented caller obligation and
further hardware/instruction investigation, **not** a claim that this change
mitigates the issue at runtime or that timing-safe mode proves the library safe.

## Verification research and hardware limits

The choice is a layered method informed by current primary material:

- [BINSEC's maintained binary checker](https://binsec.github.io/binsec-tutorial/docs/tutorial-security-properties/constant-time/)
  checks paired executions with equal public inputs and independent secrets.
  It closes a useful machine-code gap for small tractable roots; completeness,
  initialization and ISA support still matter. [Release notes](https://github.com/binsec/binsec/blob/master/CHANGES.md)
  distinguish optional multiplication/division observations from default CT checks.
  We used the current checker, not the retired binsec/rel tool.
- [CT-Prover (FSE 2024)](https://arxiv.org/abs/2402.13506) and
  [its artifact](https://github.com/S3L-official/CT_Prover) strengthen scalable
  LLVM-level verification. Its documented Clang-12 pipeline is not a drop-in
  verifier for this Rust/LLVM-22 binary. [ct-verif](https://github.com/imdea-software/verifying-constant-time)
  is another relational IR approach. Neither was claimed to have run here.
  The [BINSEC/Rel compiler study](https://arxiv.org/abs/2209.01129) is direct
  evidence that later lowering can violate an earlier IR-level CT property.
- [ctgrind](https://github.com/agl/ctgrind) motivates secret-as-undefined testing.
  We used modern [Memcheck client requests](https://valgrind.org/docs/manual/mc-manual.html),
  rather than depending on its old patch. This catches executed branch/address
  dependencies but lacks path completeness and semantic invariants.
  [Microwalk](https://github.com/microwalk-project/Microwalk) is an alternative
  dynamic trace/CI approach; it would add another trace implementation, not
  universal input coverage. It was not installed for this audit.
- [dudect](https://github.com/oreparaz/dudect) supplies the statistical testing
  model. Controls, repeated seeds and measured sensitivity are necessary to
  interpret a non-detection, which remains weaker than proof.
- [Jasmin's current CT tooling](https://jasmin-lang.readthedocs.io/en/v2026.03.2/tools/ct.html)
  illustrates the stronger long-term option of explicit security contracts and
  compilation preservation, including separate speculative/DIT concerns. It
  does not verify arbitrary Rust, and a language/backend rewrite is outside scope.

There is no single “state-of-the-art check” that proves hardware timing safety for
this Rust library on arbitrary CPUs. These tools establish different properties;
contract inventory and exact-code regression checking preserve scoped evidence
between audits without upgrading it into a proof.

[Apple's arm64 guidance](https://developer.apple.com/documentation/xcode/writing-arm64-code-for-apple-platforms)
explains timing-safe mode/DIT and supported-instruction constraints. Architectural
branch/address independence alone does not imply operand-independent timing.
[GoFetch](https://gofetch.fail/) demonstrates data-dependent prefetch leakage on
studied Apple M-series machines; this audit does not establish whether that
attack applies to this M5. Speculation, prefetch/cache-content effects and power
or frequency channels are outside our binary observation model.

[Intel's DOIT guidance](https://www.intel.com/content/www/us/en/developer/articles/technical/software-security-guidance/best-practices/data-operand-independent-timing-isa-guidance.html)
scopes operand-independent timing to supported processors/instructions and mode
settings. A generic x86-64 build and emulated taint run do not establish those
hardware assumptions, even without division. Native x86 timing remains a gap.

[Espressif's ESP32-C3 technical reference manual v1.4](https://documentation.espressif.com/esp32-c3_technical_reference_manual_en.pdf)
describes the RV32IMC core, but the reviewed CPU material does not supply a
sufficient operand-independent latency guarantee for its `mul`/`mulhu` here.
**C3 multiply timing is unknown in this audit**; no one-cycle assumption or
emulated cycle measurement substitutes for that missing evidence.

The initial commit's review reproduced a false drift failure when `CARGO_HOME`
changed: registry panic-location strings changed rodata layout. The correction
remaps the lexical and canonical spellings of HOME, Cargo home, checkout and Zig
cache to stable prefixes, ordered with the most specific prefix last. Relative
Cargo-home overrides and the default `~/.cargo` follow Cargo's resolution rules.
The final executable is rejected if any of those host prefixes remain in its bytes.

Rust remaps do not cover Zig CRT/libunwind DWARF or Darwin linker OSO paths.
`llvm-objcopy --strip-debug` removes those host-specific debug records, retaining
ordinary symbol tables (and Linux's allocated `.debug_gdb_scripts` section).
The build compares every ELF allocated section's address, size, flags and bytes,
and all Mach-O section contents, before/after stripping; any difference fails.
Pins distinguish the linked input hash from the final analyzed executable hash.

home, then requires identical snapshots and a match to the reviewed baseline.

**all five configurations passed**: the four ELF configurations also produced

A changed compiler, target CPU, profile, LTO, features, dependency lock, source,
harness, analyzer or build driver invalidates the old configuration claim.
Reachable instruction/call changes, including unchanged branch counts, also fail
drift. Data-address changes can cause conservative false alarms. External runtime
libraries, new call contexts, public-layout assumptions and hardware/mode changes
may invalidate timing claims even when these snapshots match.

For an intentional update: build with `--record` to prepare a **candidate**, inspect
its disassembly/edges/branches/addresses and tool results, then update the matching
`reviews/<name>.json` with new hashes, every branch classification, and a new
`review_note` for every affected root. A configuration change requires notes for
all roots. Re-run semantic checks and submit the evidence for peer review in the
same commit. `ct_audit_review.py --base <PR-base-sha>` rejects stale classifications
and unchanged re-audit notes; it cannot assess the truth of human review prose.
Regenerating a baseline alone does not approve it. Taint `--record` similarly
creates an unclassified candidate that must be classified before the gate passes.

The mutation tests exercise unregistered trait methods/roots, missing harness
cases, incomplete call decoding, unsupported instructions, symbol collisions,
stale/configuration-changed records and code changes with equal branch counts.
The expanded suite has 12 tests, adding host-path leakage, relative/symlink Cargo
homes, reproducibility comparison failures, out-of-trait functions, and qualified
unused-method references from other modules.
Real branch/address positive controls test both semantic engines. Unknown
transfers remain recorded gaps rather than quietly disappearing from coverage.

## Artifacts and resource use

`baselines/` contains configuration and code fingerprints; `reviews/` binds the
scope/classification to them; `evidence/` contains pinned disassemblies, symbol
and memory/branch reports (gzip), proof scripts/logs, taint XML and native timing
summaries. `gzip -dc evidence/rv32/analysis.json.gz` exposes the complete inventory.
Binaries are retained locally under ignored `target/ct-audit`, not committed.
The earlier arith-backend wrapper/traversal approach and Welch statistics were
ported; none of its assembly results are inherited as evidence for this backend.

Our `ct-x86` VM uses an 8-GiB virtual disk (about 2.0 GiB allocated on the host;
2.7 GiB used in the guest), 4 GiB RAM and four virtual CPUs. The pinned cloud image
and configuration are in `evidence/x86/lima.yaml`. Valgrind plus libc debug symbols
occupy about 86 MiB installed. The isolated opam/BINSEC tree is about 864 MiB;
audit build and Zig caches about 512 MiB, plus about 600 MiB for the fresh
reproducibility builds. The existing shared Lima cache was
3.2 GiB total, not all created by this task. Added Rust target/tool components
are recorded with sizes in the environment artifact. This stays below the
20-GB installation limit. The audit VM is stopped after the final run; other
teams' `repro-a`/`repro-b` VMs are left alone.

The equality fix in `530f289` remains the only production arithmetic change.
The Apple follow-up adds documentation and audit-only instrumentation, with no
